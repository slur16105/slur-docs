오류 화면도 서비스의 정식 화면입니다. 사용자가 **무슨 상황인지, 지금 무엇을 할 수 있는지** 이해하고 흐름을 이어갈 수 있어야 합니다.

## 언제 만드는가

- 모든 웹 프로젝트는 **404 페이지를 기본으로 제작**합니다. 잘못 입력한 주소, 오래된 링크, 존재하지 않는 하위 경로의 직접 접근을 포함합니다.
- 권한 제한, 로그인 만료, 일시 장애, 점검, 연결 끊김은 서비스에서 발생할 수 있는 유형을 검토하고 필요한 화면과 복구 경로를 준비합니다. 적용하지 않는 유형은 이유를 기록합니다.
- 일부 목록·카드만 불러오지 못했다면 [화면 상태 설계](/ux/screen-states/)의 영역 내 오류를 사용합니다. 사용 가능한 탐색·콘텐츠를 전체 오류 화면으로 덮지 않습니다. 폼 오류는 해당 입력이나 폼 안에서 해결합니다.
- 페이지 전체를 사용할 수 없을 때 독립 오류 페이지를 사용합니다. 정상 앱 셸이 작동하면 유지하고, 인증·앱 초기화에 의존해 함께 실패한다면 독립적인 최소 셸을 제공합니다.
- 존재하지 않는 페이지와 정상적인 검색 결과 없음·미등록 데이터는 구분합니다. 빈 결과에 404 문구를 쓰지 않습니다.

## 공통 화면 구성

1. **상황 제목:** 페이지의 주제를 설명하는 `h1` 하나. 숫자 코드만 제목으로 쓰지 않습니다.
2. **설명:** 현재 이용할 수 없는 내용과 사용자가 취할 수 있는 방법을 짧게 안내합니다. 원인을 모르면 추측하지 않습니다.
3. **주요 행동:** 상황을 해결하거나 안전한 화면으로 이동하는 행동 하나를 우선합니다. 보조 행동은 필요한 만큼만 제공합니다.
4. **추가 안내:** 반복 실패 시 실제 문의 경로·상태 공지, 확인된 점검 시간, 필요 시 비민감 참조번호를 제공합니다. 없는 문의 채널·복구 예정 시간을 만들지 않습니다.
5. **식별 정보:** 오류 코드·장식 아이콘은 보조 정보입니다. SLUR 로고를 표시한다면 프로젝트에 복사한 공식 SVG와 배경에 맞는 색상을 사용합니다.

슬러 디자인을 함께 사용하는 프로젝트는 기존 `empty_state.m_error`의 제목·설명·행동 구조와 토큰을 재사용할 수 있습니다. 규칙만 적용하는 프로젝트의 시각 디자인은 해당 프로젝트를 따릅니다. 독립 정적 오류 페이지에 4상태 슬롯이나 `role="alert"`를 억지로 추가하지 않습니다.

## 상황별 기본 문구와 다음 행동

아래 문구는 출발점입니다. 프로젝트의 실제 목적지·처리 결과에 맞춰 바꾸고, 실행할 수 없는 행동은 표시하지 않습니다.

| 상황 | 제목 | 설명 예시 | 주요 행동 | 보조 행동·조건 |
|---|---|---|---|---|
| 404 · 페이지 없음 | 페이지를 찾을 수 없습니다 | 주소가 올바른지 확인해 주세요. 홈이나 목록에서 원하는 내용을 다시 찾을 수 있습니다. | 홈으로 이동 | 관련 목록으로 이동. 같은 주소 새로고침을 해결책으로 제시하지 않음 |
| 403 · 권한 제한 | 이 페이지에 접근할 권한이 없습니다 | 현재 계정으로는 이 페이지를 볼 수 없습니다. 필요한 경우 관리자에게 권한을 요청해 주세요. | 접근 가능한 홈으로 이동 | 실제 권한 요청 경로가 있을 때 권한 요청. 계정 전환이 가능하면 다른 계정으로 로그인 |
| 로그인 필요·세션 만료 | 다시 로그인해 주세요 | 로그인 정보가 만료되었습니다. 다시 로그인한 뒤 이용해 주세요. | 다시 로그인 | 로그인 후 허용된 내부 경로로 복귀. 단순 미로그인은 “로그인이 필요합니다”로 조정 |
| 일시 장애 · 500 등 | 일시적으로 페이지를 불러오지 못했습니다 | 잠시 후 다시 시도해 주세요. 문제가 계속되면 고객지원에 문의해 주세요. | 다시 시도 | 접근 가능한 홈·실제 문의 경로. 문의 경로가 없으면 문구에서도 제거 |
| 점검 · 503 | 서비스 점검 중입니다 | 지금은 서비스를 이용할 수 없습니다. 점검이 끝난 뒤 다시 이용해 주세요. | 점검 안내 보기 | 실제 공지가 있을 때 제공. 공지가 없으면 확인된 시간·이용 방법을 안내하고, 작동하는 홈이나 사용자 요청 재시도 제공 |
| 연결 끊김 | 인터넷 연결을 확인해 주세요 | 연결 상태를 확인한 뒤 다시 시도해 주세요. | 다시 시도 | 저장된 내용 보기 등 실제 가능한 대안만 제공. 모든 요청 실패를 연결 끊김으로 단정하지 않음 |

세션 만료 안내에서 “작성한 내용이 보존됩니다”는 실제 복원 기능이 있을 때만 씁니다. 권한 제한 안내에는 보호된 문서명·계정·리소스 존재 여부를 노출하지 않습니다. 서비스의 보안 정책상 존재 여부를 감춰야 하면 404 안내를 사용합니다.

## 행동과 복구 규칙

- 이동은 실제 목적지가 있는 `<a>`, 재요청은 `<button type="button">`을 사용합니다. “확인”처럼 결과를 알 수 없는 이름보다 “홈으로 이동”·“다시 로그인”처럼 행동을 구체적으로 씁니다.
- 뒤로 가기는 보조 수단입니다. 외부 직접 진입·이전 화면도 오류인 경우를 고려해 **명시적인 홈 또는 목록 링크**를 항상 별도로 제공합니다. `history.length`만으로 안전한 이전 화면을 판단하지 않습니다.
- 재시도는 원래의 안전한 조회를 다시 실행합니다. 진행 중 표시와 중복 실행 방지, 성공 시 정상 콘텐츠 복귀, 재실패 시 남아 있는 안내와 대안을 제공합니다. 자동 무한 재시도·강제 홈 이동은 하지 않습니다.
- 결제·등록·저장 실패는 처리 결과를 먼저 확인합니다. 중복 실행 방지 없이 원래 쓰기 요청을 재전송하지 않습니다. 가능한 입력·작업 맥락을 보존합니다.
- 로그인 복귀 주소는 서비스가 허용한 내부 경로만 사용합니다. URL 매개변수를 검증 없이 이동 목적지로 사용하지 않습니다.
- 점검 시간은 확인된 날짜·시간대와 함께 안내합니다. 복구 시간을 모르면 약속하지 않습니다. 문의 버튼은 실제 지원 경로로 연결하고 서버 장애 시에도 접근 가능한지 확인합니다.

## 접근성과 장애 시 표시

- 페이지마다 고유한 `<title>`, `main`, 이해할 수 있는 `h1`을 제공합니다. 색상·그림·오류 숫자만으로 상황을 전달하지 않습니다.
- 동적 라우팅으로 전체 오류 화면으로 바뀌면 문서 제목을 갱신하고 새 `h1[tabindex="-1"]`으로 초점을 옮깁니다. 최초 문서 진입에서 무조건 초점을 빼앗지 않습니다.
- 같은 화면의 재시도 결과는 미리 존재하는 `role="status"`에서 알리고 초점을 유지합니다. 즉시 알려야 하는 세션 만료 등만 기존 [피드백 원칙](/ux/feedback/)을 따릅니다.
- 핵심 제목·설명·이동 링크는 JavaScript와 외부 폰트·이미지가 없어도 읽고 사용할 수 있어야 합니다. 서버·인증 장애와 함께 실패하는 API에 오류 안내를 의존시키지 않습니다.
- 320px 폭, 글자 확대, 라이트·다크, 키보드에서 안내와 행동이 잘리거나 사라지지 않아야 합니다.

## 화면과 응답 상태의 연결

예쁜 오류 화면만으로 라우팅 설정이 끝나지 않습니다. 운영 환경의 존재하지 않는 URL은 404 응답과 해당 화면으로 연결합니다. 오류 화면을 200 정상 응답으로 처리하거나 모든 잘못된 주소를 홈으로 보내지 않습니다. 서버 오류·점검도 실제 원인에 맞는 상태 코드로 응답하고, 503에서 복구 시점을 알면 `Retry-After`를 설정합니다. 정적 호스팅·SPA는 배포 환경의 라우팅과 응답 상태를 별도로 검증합니다.

근거: [MDN 404](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/404), [MDN 503](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/503).

## 예제와 검증

[패턴 · 화면 조립본](/design/screens/#404--오류-페이지)에서 404와 상황별 오류 예제를 확인합니다. 예제 파일은 **UI 조립본**이며 운영 라우트·인증·장애 복구를 대신하지 않습니다. 적용할 때 데모 제어를 제거하고 실제 목적지·요청에 연결합니다.

완료 조건은 [완료 검증 체크리스트](/quality/completion-checklist/#404--오류-페이지), 재현 방법은 [브라우저 검증](/quality/browser-verification/#오류-페이지와-복구-검증)을 따릅니다.

## 문서 사이트 적용 현황

| 화면 | 주소 | 현재 연결 범위 |
|---|---|---|
| 페이지 없음 | `/404.html` | 존재하지 않는 주소에 자동 적용, 실제 404 응답 |
| 일시 장애 | [500 안내 화면](/500.html) | 정적 안내 화면 준비. 실제 장애 응답으로 자동 교체하지 않음 |
| 점검 | [점검 안내 화면](/maintenance/) | 정적 안내 화면 준비. 전체 사이트 점검 전환은 별도 설정 |

500·점검 화면은 문서 홈에 안전한 GET 요청을 다시 보내는 링크와, 별도 도메인의 SLUR 홈페이지 이동을 제공합니다. 같은 오류 안내 URL을 새로고침하는 것을 재시도로 삼지 않습니다. 점검 종료 시간은 확정되지 않아 표시하지 않습니다.

이 사이트는 Astro 정적 빌드를 Cloudflare Pages에 배포합니다. 404와 달리 500·점검 파일은 이름만으로 장애 응답에 연결되지 않으며, 안내 주소를 직접 열면 정상 정적 문서인 **200 응답**입니다. 실제 연결 시 원래 요청 주소에서 500/503 상태와 화면 본문을 함께 반환해야 합니다. Pages Functions/Worker 등의 응답 처리 또는 사용 가능한 Custom Error Rules 설정이 필요합니다. Cloudflare 자체 장애처럼 이 사이트 코드가 실행되지 않는 상황까지 대체할 수 있다고 보장하지 않습니다.

근거: [Cloudflare Pages의 404 처리](https://developers.cloudflare.com/pages/configuration/serving-pages/#not-found-behavior), [Custom Errors의 범위와 제한](https://developers.cloudflare.com/rules/custom-errors/), [Pages Functions 미들웨어](https://developers.cloudflare.com/pages/functions/middleware/). 운영 연결·점검 전환·해제·검증 절차는 저장소 `docs-internal/site-error-operations.md`에 기록합니다.
